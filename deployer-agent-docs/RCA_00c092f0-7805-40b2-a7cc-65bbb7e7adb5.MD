# RCA — crm-production-3 — Google sign-in bounces to /login & passkeys 500

## Summary
Your hypothesis is CONFIRMED by production. Every unauthenticated route that touches an org‑scoped collection raises `OrgScopeError` → HTTP 500 because the production `organizations` collection has **zero documents** — there is no `is_default: true` organisation to pin a request to. The running image is the PRE‑fix image; `org_bootstrap.py` is not deployed yet.

## Evidence

### 1. Database (db: `crm-production-3-test_database`, active run 00c092f0)
- `organizations` collection **exists but is EMPTY** — `find` returns `count: 0`. No document at all, therefore none with `is_default: true` / `status: "active"`.
- `users`: **11 documents**, of which **1 has `role: "super_admin"`**. (Note: these users pre‑date the multi‑tenant change — the DB is NOT fresh/empty; it holds 176 collections of migrated data. Only the `organizations` collection is empty.)

### 2. Backend logs (since last deploy)

  → `POST /api/auth/google-session HTTP/1.1" 500 Internal Server Error`

## Root cause
Multi-tenant scoped-DB proxy requires an active organisation; production has an empty `organizations` collection, so the per-request fallback to the `is_default` org finds nothing and raises `OrgScopeError` (500) on every unauthenticated route. The migration (`scripts/migrate_organizations.py`) that seeded the default org in preview was never run against production, and nothing auto-created it until your pending fix.

## Fix
- **Code / E1 (redeploy the pending fix):** Deploy the build containing `backend/org_bootstrap.py` so organisation #1 is created at startup before owner-bootstrap and seeding. This image is not yet live.
- **Caveat to verify before/at deploy:** `org_bootstrap` must trigger when the `organizations` collection is EMPTY, not only when the whole database is empty — production already has 176 collections and 11 users, so a "database is empty" guard would NOT fire here and the bug would persist. Confirm the guard keys off an empty/absent `organizations` collection.
- **Existing data caveat:** The 11 pre-existing users (incl. the 1 super_admin) predate multi-tenancy. After org #1 is created, confirm these users get associated with the default org (your cross-org account lookup should handle sign-in, but any org-scoped data they own may need back-filling with the new org id).
- Alternatively a one-time run of `scripts/migrate_organizations.py` against production would seed the default org immediately, but the startup bootstrap is the durable fix.
